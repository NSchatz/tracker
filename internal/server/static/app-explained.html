What the Android app shows

tracker's phone app keeps one short label per thing on the screen itself. The paragraphs that explain those labels live here and in the app's own explanation screens, which carry exactly the same words - one affordance per card opens the screen for that card.

Permissions

tracker needs location access to report where this phone is. The next screen is the system permission prompt.

To keep reporting when the app is closed, tracker needs background location. This is a second, separate prompt - Android will not ask for both at once.

On Android 11 and later the permission prompt has no "Allow all the time" option - it can only be set in system settings. Open settings, choose Permissions then Location, and pick "Allow all the time".

Android will no longer show the permission prompt for this app. Open settings and grant location access there.

tracker can collect location continuously, including while the app is closed.

Degraded states, named rather than tolerated

Background location is not granted. Collection works while the app is open, but Android will stop it once the app is closed - the trail will have gaps.

Only approximate location is granted, so positions may be off by a city block. Grant precise location for an accurate trail.

Notifications are blocked, so the ongoing "sharing your location" notice will not be visible. Collection still runs.

Server settings

The device token is stored unencrypted in this app's private data on the phone until secure storage ships (roadmap C3). On a non-rooted phone with a lock screen no other app can read it, but anyone with root, an unlocked bootloader or a full-device backup can. Cloud backup of the app's data is already switched off.

Save reports the verdict of validating what you typed, never a blanket "it worked". A save that happened says "Saved to this device"; one that did not says "Not saved" and why. The two verdicts do not share a prefix on purpose - "Saved" alone reads as part of "Not saved" to anyone skimming. A URL the app will refuse to use says so on the card in a few words - "Not saved: No device token set" - and the full sentence naming what to fix is shown at the top of the in-app explanation this page mirrors. A release build also refuses plain http://, so a shipped app cannot send a bearer credential in the clear.

The counters, and the set each is counted over

When something stops collection or delivery, the card names the KIND of trouble in a few words - server settings incomplete, location permission lost, background location not allowed, Android refused collection, reporting failed, device token rejected - and the sentence describing exactly what happened is shown at the top of the in-app explanation. The sentence is kept off the card because it is not ours to keep short: a network failure or an Android exception supplies its own wording, and a paragraph on a phone card is a paragraph nobody reads.

When the phone reboots, collection starts again on its own if you had it running: the app remembers that you asked for it and restarts as soon as Android reports the boot finished, with nobody touching the phone. If you stopped collection before the reboot it stays stopped. Two things can prevent the restart, and the card says so rather than looking like a deliberate stop - it reads "Enabled, not running" and names the reason, with the full sentence at the top of the in-app explanation. The reasons are that "Allow all the time" location access is not granted, which Android requires before anything may start location collection in the background, and that the server settings on this phone are incomplete, so there is nowhere to report to. One case the app cannot recover from at all: after a force-stop, Android delivers no boot signal to this app until you open it again, so collection stays stopped until you do.

Fixes are saved on this phone until the server confirms them, so going offline delays reporting instead of losing it. "dropped" means a fix the server permanently refused, one older than 90 days, or one discarded because the offline queue filled up.

Delivered
Fixes the server accepted during THIS run of the app, counted from the moment collection started. It is not a lifetime total and it is not restored from disk: after a restart the honest answer is "not recorded", not a stale number. It counts an idempotent replay the server already had as delivered, so it can over-count a fix that was sent twice.
Queued
Fixes currently sitting in the on-disk queue, read from the queue itself rather than counted in memory - which is why it survives a restart when the other two do not. A non-zero value is normal, not an error: it is what the queue looks like while the phone is offline, and it is the number that says nothing has been lost.
Dropped
Fixes measured during this run that will never reach the server. It is shown as prominently as Delivered on purpose: an app that only ever displays its successes is how silent fix loss stays silent.

A counter that has never been measured reads not recorded, never 0 and never a dash. A measured zero still reads 0, because "we checked and it is none" and "we never checked" are different facts and a reader deciding whether their family's trail has a hole in it needs to be able to tell them apart. If the queue directory cannot be read at all, the queued figure alone reads unavailable and everything else on the screen keeps working.

Current, or last known

While collection is running and a fix has arrived within the reporting interval, the counters are labelled as current. When collection is stopped, has been killed by the system, or has produced no fix for longer than that interval, the same counters are labelled last known with the time they were last updated. A frozen readout is never presented as a live one, and when collection resumes the counters go back to reading as current.

Alerts, and the crossings list behind them

The alerts card shows exactly one delivery state, in a few words, and the paragraph for each one is on the screen's own "About alerts" page. The states are: still being checked; no viewer token set; alerts cannot be shown, because notifications are blocked for this app; not registered because the server refused the token, or because it could not be reached; not receivable for one of four reasons - this phone has no push address, this server has no push backend configured, this server uses a backend this app cannot receive from, or this server does not report which backend it uses; and armed. Only the last of those means a crossing will arrive as a notification, and nothing else is ever shown as armed.

The crossings list is read from the server rather than assembled from the notifications that arrived, so a crossing the push backend dropped is still there. "No crossings recorded yet" means the server was asked and answered with nothing. Each "Crossings unread" state means the list could NOT be read - a rejected token, a server that could not be reached, or an answer this app could not parse - and none of those is an empty family log.

A push that does not carry a complete crossing - its kind, the device name, the Place name and the direction - renders no notification, and is counted on the card instead. No missing part of it is guessed at, and the count is shown rather than kept quiet, because a discarded push is an alert somebody did not get.

The push backend holds only four pending alerts per phone, one per device-and-place pair, and then discards the rest. The list, read back from your server, is the record; the notification is not.

The viewer token is stored unencrypted in the app's private data, exactly as the device token is, until secure storage ships. It reads the whole family's crossings, so treat it as the more sensitive of the two. Cloud backup of the app's data is already switched off.
