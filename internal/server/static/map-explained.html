What the live map shows

This page explains the words on tracker's live map. The map itself keeps its labels to a few words on purpose; the methodology lives here so that the surface stays readable on a phone.

Watching your family

A viewer token is a read credential for one family. Paste it into the map's token field and choose Watch. The map then does two things: it asks the server once for the family's devices (so it can tell "this family has no devices" apart from "still connecting"), and it opens a long-lived event stream so positions update without a reload.

A token is a live credential. Anyone holding it can see where your family is, so treat a /map?token=... link the way you would treat a password. The map never stores the token anywhere except the field you typed it into, sends it to nobody but the server that served the page, and the page is sent with a Referrer-Policy: no-referrer header so the address bar's token is never handed to the map tile host.

Connection status is a separate thing from any device's state. The status line reads connecting, live, connection interrupted, or names a refused token. When the feed is interrupted, every device on the page is marked (last known - unconfirmed): the map keeps showing you the last thing the server said rather than freezing a green map that implies it is still true. When the feed comes back the annotation clears on its own, with no reload, and no device is ever removed to make this happen.

What the state words mean

The server decides each device's state and the page renders exactly the word it was sent. The page does no clock arithmetic, so a browser with a wrong clock cannot disagree with the server about whether a phone is live. The four states, and the wire tokens behind them, are:

live now (live)
The server heard from this phone inside the live window. Where it is shown is where it is.
seen recently (recent)
Past the live window but inside the recent one. The position is real but is not this minute's.
not seen lately (stale)
Older than the recent window. The marker is the last position the server holds, which may be hours old. A phone that is off, out of signal, or has had collection stopped reads this way.
no position recorded (no-position)
The server holds no position for this device at all: it has never reported, or retention purging has deleted every fix it had. This is an absence, not a zero, and the device gets no map marker at any coordinate - a marker at 0,0 would be a real place in the Gulf of Guinea, and showing one there would be a fabricated answer.

A device can also read - position not readable. That means the server described the device but the coordinate that came with it was missing or was not a number. The device is listed as present and is deliberately left off the map, because guessing a position is worse than admitting there is not one.

Why the counts name their set

"3 of 5 on map, 2 without position" is written that way because "3 devices" is a figure a reader takes for the whole family. The devices left off the map are counted in the same line rather than dropped from the total, so the number you see is never quietly smaller than the family.

"1 of 40 updates unreadable" counts the stream events and device rows this page was handed against the ones it could not read. One bad update in forty and forty in forty are very different situations, and a bare "1 rejected" cannot tell them apart. An update the page cannot read costs only itself: every other device, the map and the status line keep drawing, and the stream is not closed.

What the map talks to

Everything the page needs - its stylesheet, its script, the vendored Leaflet library, the device list and the event stream - comes from the tracker server you pointed your browser at. The single third party is the map tile imagery from tile.openstreetmap.org, and no token is ever sent there. A Content-Security-Policy sent with the page pins that down in the browser itself: nothing else may be loaded and nothing else may be connected to, and the policy names no reporting endpoint, because a reporting endpoint is one more place a URL carrying a token could be sent.
